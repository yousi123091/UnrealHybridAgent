# 第二版路线图（以及第一版为什么故意不做这些）

第一版的目标不是"功能多"，而是**一个能被信任的最小闭环**：挑方式 → 执行 → 复验 → 不通过就降级 → 全程留证。
凡是会削弱"可信"这件事的功能，都推到第二版。

下面每一条都写清楚三件事：**为什么第一版不做**、**它现在是怎么被替代的**、**要做的话打算怎么做**。

---

## 0. 明确的非目标

有些事不是"还没做"，而是**第一版就不打算做**——写下来是为了别在下一版里悄悄地做掉：

- **不做无人值守的全自动改工程。** 检测器结论不可信时（`actionable=False`）框架必须拒绝动手，而不是"尽力而为"。
- **不做删除类操作**（`never_delete_assets`）。删除不可逆，自动化收益远小于风险。
- **不让模型自由生成计划然后直接执行。** 计划必须先能被人读懂（`uha plan` 先看），才允许执行。等确定性路径跑稳了，再考虑把模型接在"生成初稿"这一环。

---

## 1. 全场景自动浮空检测 —— 不做

**为什么不做**：实测四种几何做法在真实建筑场景（1184 个 Actor）上误报率 48% / 95% / 77% / 49%。场景是多峰的（地坪 ≈0、主殿台面 ≈856、屋顶 ≈2000+），**不存在统一的"地面"**。提供一个 50% 误报率却"看起来能自动干活"的检测器，是最危险的假绿。数据见 [`FINDINGS.md#f1`](FINDINGS.md#f1)。

**现在的替代**：显式地面参照物（`ground_ref`）+ 限定巡检区域（`region`）+ 三道独立门槛。要巡检就明确告诉框架"地面是哪块板、看哪片区域"。

**要做的话**：靠包围盒几何是不够的，得引入**方向性/语义**信息，候选路线：

1. 用 MCP 已有的 `actor/line_trace` 对每个构件向下打射线，把"打到的第一个面"当支撑面；难点仍是**重檐屋顶压屋顶**和**台阶踏面不水平重叠**（F1 里那两类误判的根因）。
2. 用 `get_actor_folder` / 命名前缀做**语义分层**（`EXT_StairB_*`、`*_Roof`），按"层"而不是按 Z 值判地面。
3. 引入 VLM 作为**候选提议器**（只提议"哪几个可疑"，结论仍由几何判定），而不是让 VLM 下结论。

---

## 2. 精确落回地面 —— 只做了近似下压

**为什么不做**：把浮空件精确放回地面需要**射线检测 + 包围盒对齐**，是个独立的问题（还要处理"落下去会不会穿模/压到别的东西"）。

**现在的替代**：`plan_floating_repair(drop_by=...)` 往下压一段调用方给的距离，并且在计划描述里明确写"这是近似修正，不是精确落地"——**不把近似值说成确切结果**。

**要做的话**：MCP 的 `actor` 域已经有 `line_trace` 与 `spawn_on_surface_raycast`，通路是现成的：

```
对目标件 XY 上取几个采样点 -> 分别向下 line_trace
-> 取命中面 Z 的稳健值（中位数，滤掉命中的装饰件）
-> 换算成绝对 location（绝对定位是幂等的，天然避开 F3 那一类重试风险）
-> 复验：包围盒底边 - 支撑面 |≤ ground_tolerance|
```

需要先解决：如何区分"支撑面"和"恰好挡在下面的装饰件"（可用命中面的 `actor_label` 做白名单/黑名单）。

---

## 3. 批量操作 —— 只有安全策略，没有执行路径

配置里有 `safety.max_actors_per_batch`，router 也有 `rule_batch`（≥5 个对象 → 结构化通道），但**没有批量的执行实现**：现在仍然是"一个 skill 一个对象"。

**为什么不做**：批量的正确性风险不成比例——一次改 200 个对象，出问题就是 200 个对象一起错，而验证成本（逐个复验）反而更高。

**要做的话**：分两步。① 先在结构化通道里把"批量改值"做成**一次调用 + 一次全量回读**，验证按集合比对（哪个对不上就点名）；② 再考虑分块（chunk）执行与单块失败回滚。**批量与"不可幂等动作"要特别小心**：批量做相对位移如果被重试，会一次性重复生效 200 次。

---

## 4. 动态重规划 —— 刻意不做

**为什么不做**：真正的动态决策点只有一个——"这一步用哪种方式执行"，那件事已经由 Router 负责。计划层再做一次动态决策，就会出现**两层同时做决策**，互相打架后连"哪一层选错了"都说不清。

**要做的话**：只做"失败后按规则替换某一步的参数"（例如复验发现还有浮空 → 再补一次修正步骤），并把替换动作**写进日志**（重规划本身也要可复盘）。

---

## 5. 让模型参与计划生成 —— 只到"生成初稿"

现在的自然语言解析是关键词 + 阈值（`parse_actor` / `parse_delta`），产出初稿并**如实报告**"这是推断结果，请核对"。它不假装懂了。

**要做的话**：把模型接在**生成初稿**这一环，输出必须过三关才允许执行：① 解析成结构化 `Plan`；② 每个 skill 的参数通过 schema 校验；③ 执行前打印人类可读的计划。**不做**"模型直接生成 tool call 序列并执行"。

---

## 6. GUI 通道的自动标定 —— 现在是"不标定就拒绝执行"

`vision.roi.*`（World Outliner / Details / Viewport / Toolbar）与 `desktop.editor_focus_point` 现在是 `None`。未标定时 GUI 相关路径**明确报错**，而不是盲点坐标——这是刻意的（盲点一次可能就改错了东西）。

**要做的话**：写一个半自动标定流程——截一张全屏图，让用户框选几个面板（或按 UE 默认布局 + 分辨率算默认值），把结果写回本地 `agent.config.json`。注意分辨率/缩放一变就得重标（本机 2560×1600 / scaleFactor 1.4997，逻辑 1707×1067）。

---

## 7. VLM 语义定位 —— 依赖外部服务

当前 Agent-TARS 的 `vlmConfigured=false`，所以"语义级视觉定位"不可用。框架里 `vision.backend` 已经预留了 `heuristic | vlm` 两种，VLM 只作为**可选增强**，未配置时对应的检查记 `skipped`（不影响确定性判断，也不会被误判成失败）。

**要做的话**：配置 VLM 后，让它只承担"候选提议"和"证据描述"，**不承担 pass/fail 结论**（结论仍来自几何与结构化回读）。

---

## 8. UE_PYTHON / UE_COMMANDLET 通道 —— 代码在，活体环境没验证过

`doctor` 里这两条一直是 `DOWN`：

- `UE_PYTHON`：需要编辑器开启 `bRemoteExecution=True`（默认关）。**还没在重启后的编辑器上验证过**。
- `UE_COMMANDLET`：与"已经打开的编辑器会话"互斥，本机编辑器常开，所以一直不可用。

**要做的话**：在干净的（未开编辑器的）环境里跑一遍这两条通道的契约测试，并补齐它们缺失的 op（`viewport_screenshot` 目前只有 MCP 有）。

---

## 9. 幂等性声明只覆盖了一个 skill

`Skill.is_idempotent()` 目前只有 `actor_move` 真的声明了（相对位移 → 不幂等；绝对定位 → 幂等）。其余 skill 走默认值 `True`。

**要做的话**：逐个过一遍并写进测试：

| skill | 应当声明 | 理由 |
|---|---|---|
| `actor_find` / `actor_inspect` | 幂等 | 只读 |
| `visual_inspect` | 幂等 | 只读（截图 + 几何判定） |
| `level_save` | 幂等 | 保存两次 = 保存一次（`UNREAL_MCP` 那条路已验证过重复调用无害） |
| `actor_move` 相对位移 | **不幂等** | 已完成 |
| 未来的批量/删除类 | 必须逐个论证 | 默认 `True` 在这里是危险默认值 |

> 顺带一条原则性问题：`is_idempotent` 的**默认值给 `True` 是错的默认**——拿不准时应当保守。现在保留 `True` 只是为了不误伤已有的只读 skill；新增写操作 skill 时必须显式声明。

---

## 10. 健康度记账：从"全局成功率"到"按任务类型记账"

第一版：一个通道一个全局成功率 + "连续失败 N 次冷却"。

**实测出来的问题**（今天踩的，复盘见 [`FINDINGS.md#f5`](FINDINGS.md#f5)）：全局成功率会把**通道不擅长的任务**混进来。只读巡检退到 HYBRID 必然 `NOT_SUPPORTED`，但那是"不匹配"，不是"不健康"。今天的修法是**把 `NOT_SUPPORTED` / `UNEXPECTED` 排除出账本**，但那只堵住了最大的一个洞。

**要做的话**：账本按 `(skill 类别, method)` 记，例如 `read_only × HYBRID` 与 `mutation × HYBRID` 分开算；只有"同一类任务上连续失败"才冷却。

---

## 11. 并发与排队

Computer Use 那边有 `DesktopLock`（单持有者 + FIFO + TTL 120s），框架自己**没有**跨进程的任务队列：两个 `uha` 进程同时跑会互相抢桌面。

**要做的话**：在 `uha` 入口加一把项目级的锁文件（`.state/run.lock`），或者干脆把 `DesktopLock` 的语义提升到"整台机器的 UE 会话"这一层。

---

## 12. 配置与多工程

现在 `config/agent.config.json` 只描述一个工程 + 一个关卡。`ue.search_paths.project_roots` 是空的。

**要做的话**：按工程/profile 分配置文件（`config/profiles/*.json`），把"关卡相关"的参数（试件 label、巡检区域、地面参照物）抽成**场景清单**，避免每次都手打 `--region`。

---

## 下一版先做什么（建议顺序）

1. **精确落回地面**（§2）——它把 Demo2 从"演示"变成"能用的功能"，而且射线通路已经现成。
2. **幂等性声明补齐 + 危险默认值收紧**（§9）——成本极低，直接降低"改坏工程"的概率。
3. **健康度按任务类型记账**（§10）——在同类任务更多之后，全局成功率一定会开始误导选路。
4. **GUI 标定流程**（§6）——这是目前"降级链跑不满"的唯一硬阻塞。
5. 其余按需。

- 统一 op 词汇表 + 多协议适配（MCP 已实测；Python/Commandlet 待活体验证）
- 规则 + 成本的可解释选路，输出完整降级链与被淘汰原因
- 三态验证（`passed` / `failed` / `skipped`），弱检查降为 `advisory`
- 不可幂等动作的重试护栏（F3 的根治）
- 步骤级通道建议（`prefer_method`），只重排不缩链
- 逐步骤可复盘的 jsonl 日志 + 独立只读对账工具 `tools/observe.py`
- 两个端到端演示 + 195 项离线回归 + 24 项路由回归
